## 2. Surprises / discrepancies found

**D1 — "NHANES" is fully synthetic, not real CDC NHANES data.** [data/nhanes.csv](../data/nhanes.csv) is generated entirely by [scripts/download_nhanes.py](../scripts/download_nhanes.py)'s `generate_nhanes_dataset()`: ages, blood pressures, cholesterol, BMI, HbA1c are drawn from independent `np.random.normal` distributions and the outcome label from a hand-written logistic model, seeded `np.random.seed(42)`. We confirmed this by regenerating the dataset in-memory and it is byte-identical to the file on disk. **There is no real NHANES ingestion code anywhere in the repo** (no `nhanes.gov` fetch, no `.XPT`/SAS transport parsing, no NHANES cycle/survey-weight handling). This is a significant claim mismatch: the project brief and README describe this as "the CDC NHANES cohort," but it is a synthetic cohort with an NHANES-like schema and a name borrowed from the real survey. This must be stated plainly in `FINDINGS.md` and the report's limitations section — any "generalizes across a real dense EHR cohort" claim is not supported by this dataset.

**D2 — UCI dataset is real (processed Cleveland subset) and its size matches the paper (N≈237 train).** `data/uci_heart.csv` has 297 rows, 9 features + `heart_disease_risk`; after the 80/20 split, the training partition is 237 rows (297×0.8=237.6→237), matching the paper's stated "sparse, N≈237." NHANES full CSV is 2500 rows → 2000 train rows, matching "dense, N≈2000." So the *brief's* N figures are correct; it is specifically the *provenance* of the NHANES data (D1) that is misrepresented, not its scale.

**D3 — Two different, only partially overlapping constraint checks are in use.** Graph-edge pruning (`check_clinical_violations` in `calg.py`) ORs *hard* violations (immutables, age decrease, per-step age-horizon cap) with *directional* violations (BP/cholesterol/HbA1c/etc. must move the "correct" way beyond a feature-specific epsilon). But `compute_cvr` in `benchmarks/metrics.py`, used to report the headline "CVR%" in Table 1, calls `check_hard_violations` **only** (immutables + age-decrease), with `check_step_horizon=False`, and evaluates it **once, source→final target**, not per hop. So the reported "0.0% CVR" for CARE-LG is a real, true statement about hard violations end-to-end, but it does **not** by itself certify that directional/soft constraints hold along the path — those are enforced by construction during graph pruning, but never independently re-verified by the metrics module. This gap is exactly what Phase 3 (decoded-space verification) is for, and we implement it against the **full** `check_clinical_violations` definition (hard + directional), consecutive-hop and source→final, to give a strictly stronger post-hoc guarantee than the existing `compute_cvr`.

**D4 — No seeding of `torch` or Python `random` anywhere in the repo.** `grep` for `manual_seed|random.seed` across `src/`, `scripts/`, `benchmarks/`, `configs/` finds only three `np.random.seed(seed)` calls (data loader's synthetic-EHR fallback, NHANES generator, and one `np.random.choice` for query-instance subsampling in `run_benchmarks.py`). **VAE and classifier weight initialization, dropout/batch shuffling order, and the VAE reparameterization noise are never seeded.** We verified this empirically (§3): rerunning the *unmodified* pipeline with `seed=42` reproduces NHANES headline numbers closely but reproduces UCI numbers only loosely, because UCI is small enough that training-noise variance dominates. All new code in `experiments_v2/` seeds `numpy`, `python random`, and `torch` (`torch.manual_seed`, and `torch.mps.manual_seed` / CUDA equivalent where applicable) explicitly per run, per Hard Rule 3.

**D5 — Baselines are custom reimplementations, not the cited libraries.** See table above (component "Baselines"). `carla-recourse` is an unused dependency. This matters for Phase 5: we treat the existing DiCE/FACE/GrowingSpheres code as-is (documented as "our lightweight reimplementations, not the original released code") rather than pretending they are the papers' reference implementations.

**D6 — `build_calg_graph`'s per-edge Riemannian distance is the dominant cost, and is trivially batchable.** Each edge independently calls `torch.autograd.functional.jacobian` on the decoder at the edge midpoint. This is correct but issues one Jacobian call per edge. We verified a fully vectorized reformulation using `torch.func.vmap(jacrev(decode))` over all edge midpoints at once, run on CPU, reproduces the scalar per-edge `riemannian_distance` to float32 precision (max abs error `5.96e-8` over a random sample of 20 edges) while being roughly two orders of magnitude faster (NHANES: 160,000 edges in 0.83s vectorized vs. ~15s in the existing tqdm loop on MPS, vs. ~373s in a naive one-call-at-a-time microbenchmark on MPS). We use this vectorized routine (`experiments_v2/lib/riemannian_batch.py`) **only** inside the new `experiments_v2/` grid code, to make the 2×2(×λ)×5-seed×2-dataset grid tractable; it is a pure performance optimization with no behavioral change, added as new code alongside — not instead of — the original `src/graph/riemannian.py`, which is untouched.

**D7 — MPS is slower than CPU for this workload.** On this machine (Apple M2), single-edge Riemannian distance calls average 2.33ms on MPS vs. 0.35ms on CPU (kernel-launch overhead dominates at this tiny problem size). The original pipeline calls `get_device()` (CUDA→MPS→CPU) and is left unchanged. The new `experiments_v2/` grid code defaults to CPU for the graph-building phase specifically because of this, documented in `CHANGES.md`. This does not affect the reported latency metric (which times only the Dijkstra search call, not graph construction).

**D8 — Attaching a held-out test patient to the CALG needs its own rule, and the original benchmark's rule is more lenient than the graph's own edge rule.** `src/graph/calg.py`'s `build_calg_graph` never handles external test patients at all — the "core" pipeline (`scripts/test_day2.py`) only searches for recourse among nodes that are already IN the graph. Only the separate `benchmarks/run_benchmarks.py` harness bridges a test patient in, by searching the WHOLE train set for a "valid entry node" using `check_hard_violations(..., check_step_horizon=False)` — i.e. hard constraints only, no directional check, no per-step age-horizon cap — then starting Dijkstra from that node with the entry hop itself untimed/uncosted. We found empirically that gating a query's entry edges with the graph's own (stricter) rule — `check_clinical_violations` with `check_step_horizon=True`, restricted moreover to only its k nearest Z-neighbors — leaves most patients with zero valid entries (15/25 UCI seed-0 high-risk patients had **no** feasible entry among their 40 nearest latent neighbors, versus a mean of 34.2 feasible entries somewhere in the full 237-node graph), collapsing hard-mode success to ~4% for reasons that have nothing to do with the metric/constraint ablation this project is about. `experiments_v2/lib/graph_build.py::build_query_edges` therefore attaches each query to **every** train node (not k-restricted) and gates hard-mode pruning with the original benchmark's relaxed hard-only/no-horizon rule, while still scoring soft-mode severity `v(x_i,x_j)` with the full hard+directional definition. This restored hard-mode success to 64% (UCI) / 100% (NHANES) on a seed-0 pilot, in the range of the originally reported numbers. Documented here and at the call site; see also CHANGES.md.

**D9 — VAE reconstruction error is large relative to the constraint tolerances.** Measuring `|decode(encode(x)) − x|` on the full training set (both datasets, seed 0): mean absolute error is ≈5.8–6.2 years for `age`, ≈0.46–0.49 for the binary `sex` feature (i.e. barely better than chance at recovering which class a patient belongs to), and tens of mmHg/mg-dL for blood pressure and cholesterol (full table in `experiments_v2/results/vae_reconstruction_error.csv`, generated by Phase 3 diagnostics). This single fact is the direct explanation for Phase 3's headline finding: hard-mode graph pruning is exact on the *original, encoded* feature values (by construction, decoded-space CVR is not zero — see FINDINGS.md), so "0% CVR" is a true statement about the graph's internal bookkeeping but not about the trajectory a patient would actually be shown after decoding. This is a property of the existing `TabularVAE` architecture/training recipe (small hidden width, plain summed MSE reconstruction loss across heterogeneous feature scales, 25 epochs) — we did not retrain it differently, per Hard Rule 6.

## 3. Reproduction of headline numbers

We reran the **unmodified** `benchmarks/run_benchmarks.py::run_all_benchmarks` end-to-end (fresh model training — the cached `models/{dataset}/*.pt` checkpoints were *not* reused, so this exercises the model-training nondeterminism), redirecting only the output path (via a `PROJECT_ROOT` monkeypatch to keep the original code untouched) so that `benchmarks/` and `models/` were not written to. Script: `experiments_v2/repro_check/run_repro.py`. Raw logs: `experiments_v2/repro_check/repro_log.txt`. Both runs used `seed=42`, same as the numbers already committed in `benchmarks/{dataset}/results.csv`.

| Dataset | Metric | Existing committed value | Reproduced (this session, same seed=42) | Match? |
|---|---|---:|---:|---|
| UCI | CARE-LG Success % | 47.62 | 63.64 | **No** — large gap |
| UCI | CARE-LG CVR % | 0.00 | 0.00 | Yes |
| UCI | CARE-LG KDE | −7.167 | −7.238 | Close |
| UCI | CARE-LG Latency (s) | 0.0005 | 0.0005 | Yes |
| NHANES | CARE-LG Success % | 99.0 | 98.0 | Close |
| NHANES | CARE-LG CVR % | 0.0 | 0.0 | Yes |
| NHANES | CARE-LG KDE | −8.2879 | −8.1835 | Close |
| NHANES | CARE-LG Latency (s) | 0.0002 | 0.0003 | Close |

**Finding:** CVR (0%) and latency reproduce exactly / near-exactly on both datasets — those are structural properties of the pruned graph and the Dijkstra call, not sensitive to training noise. NHANES success rate and KDE reproduce closely (dense cohort, N=2000, averages over many query patients). **UCI success rate does not reproduce** (47.62% originally vs. 63.64% freshly retrained) — a 16-point swing on the paper's headline sparse-cohort number, directly attributable to Discrepancy D4 (unseeded VAE/classifier training) combined with UCI's small N. This is reported, not hidden, and is the empirical motivation for Phase 2's mandatory multi-seed harness and Figure E (UCI seed-variability box plot): **the paper's single-seed 47.6% UCI point estimate is not a stable number**, and any revision of the paper must report it as a mean±std over seeds, not a point estimate.
